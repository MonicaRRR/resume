# 中文 AI 简历创建与优化器 MVP 设计

## 1. 背景与目标

本项目是一个本机单用户 Web 应用，帮助中文求职者围绕目标公司和职位描述（JD）创建、优化并训练使用一份可信的简历。

MVP 必须完成以下闭环：

1. 用户创建求职项目并输入公司名称和中文 JD。
2. 用户上传现有简历，或通过表单和问答建立个人经历。
3. AI 分析 JD，并仅依据用户已经提供的事实提出补充问题和修改建议。
4. 用户审阅修改前后对比并确认修改。
5. 系统优先复用上传简历的模板；不能可靠复用时使用预置模板。
6. 用户导出 PDF、DOCX 或结构化 JSON。
7. 用户基于同一 JD 和简历进行文字模拟面试与笔试练习。

MVP 只支持中文。应用默认在用户本机运行，数据默认不离开本机；只有在用户主动选择 API 或 Codex 模式并确认后，必要上下文才会发送给对应服务。

## 2. 已确认的范围

### 2.1 包含

- 本机单用户 Web 应用，无需登录。
- 公司名称录入；公司名称可选，JD 必填。
- 求职类型为校招、实习或社招；校招与实习简历固定以一页 A4 为目标，社招不限页数。
- PDF、DOCX、TXT 简历上传。
- 从可提取文本的 PDF 读取内容和基础版面特征。
- 从 DOCX 读取内容、字体、字号、颜色、段落、间距和基础分栏信息。
- 无简历时使用引导表单和 AI 追问创建简历。
- 统一的结构化简历数据模型、事实来源标记和版本管理。
- JD 关键词、职责、能力、匹配项和缺口分析。
- 修改建议、修改理由、逐项差异审阅和人工确认。
- 四套预置中文、ATS 友好模板，以及 AI 自动选择和用户手动切换。
- 实时 A4 预览。
- PDF、DOCX、JSON 导出。
- OpenAI-compatible API 接入。
- 本机 Codex CLI 自动调用。
- 为 Codex 聊天页面生成可复制或导出的完整上下文。
- 文字模拟面试、追问、点评和改进建议。
- 岗位笔试练习、提示、作答和解析。

### 2.2 不包含

- 本地模型实际调用；只保留模型适配器接口。未来默认候选模型为 Qwen3.8 27B。
- 账号、权限、多用户或团队协作。
- 云同步、在线托管和分享链接。
- 语音面试、实时音视频或语音转写。
- 扫描版 PDF 的 OCR。
- 像素级还原 PDF 模板。
- 手机原生应用或桌面安装包。
- 自动投递职位或代替用户参加真实笔试。

## 3. 技术路线

采用轻量自建架构，并借鉴开源简历项目的结构化数据与打印预览思路，不直接建立在重型完整简历平台上。

### 3.1 前端

- React、TypeScript、Vite。
- React Router 管理项目首页、工作台、训练区和设置页。
- TanStack Query 管理服务端状态。
- Zustand 管理尚未保存的编辑状态、预览状态和当前版本。
- Zod 在浏览器端验证 API 数据。
- CSS print media 生成 PDF 打印版；A4 预览与打印共用模板组件。

### 3.2 后端

- Python 3.12、FastAPI、Pydantic。
- SQLite 保存结构化数据和版本；SQLAlchemy 2.0 负责持久化。
- `python-docx` 解析和生成 DOCX。
- `PyMuPDF` 提取 PDF 文本、文本块位置、字体和颜色。
- 独立的模型适配器负责 API 与 Codex 调用。
- 上传文件、临时渲染文件和导出文件存放在本项目本地数据目录，不写入代码目录。

### 3.3 模块边界

- `projects`：求职项目、公司和 JD。
- `resume`：统一简历模型、事实来源、校验和版本。
- `ingestion`：PDF、DOCX、TXT 解析及质量报告。
- `analysis`：JD 分析、匹配分析、补充问题和简历补丁。
- `providers`：OpenAI-compatible、Codex、未来本地模型适配器。
- `templates`：预置模板、导入样式描述、选择和渲染。
- `exports`：PDF、DOCX、JSON 导出。
- `practice`：模拟面试和笔试练习。

模块之间只传递 Pydantic 定义的数据对象，不传递未约束的字典或模型原始文本。

## 4. 核心数据模型

### 4.1 求职项目 `JobProject`

- `id`
- `title`
- `company_name`
- `application_type`：`campus`、`internship` 或 `experienced`。
- `job_description`
- `job_analysis`
- `active_resume_version_id`
- `selected_template_id`
- `created_at`
- `updated_at`

### 4.2 简历 `ResumeDocument`

- `basics`：姓名、联系方式、所在地、目标职位、个人简介。
- `education[]`
- `work_experience[]`
- `projects[]`
- `skills[]`
- `certificates[]`
- `awards[]`
- `custom_sections[]`
- `section_order[]`
- `layout_profile`

经历、项目和教育条目都包含稳定 ID。可被 AI 改写的字段使用 `SourcedText`：

- `value`：当前文本。
- `source_fact_ids[]`：支持该文本的事实 ID。
- `origin`：`upload`、`questionnaire`、`manual` 或 `ai_rewrite`。
- `confidence`：解析置信度，不代表事实真实性。

### 4.3 事实 `Fact`

- `id`
- `category`
- `statement`
- `source_type`
- `source_location`
- `user_confirmed`

AI 不得创建无法关联到事实的公司、职位、项目、技能、数字、日期、证书或成果。缺少必要信息时，必须生成问题，而不是补写推测内容。

### 4.4 版本与补丁

每次正式修改创建不可变的 `ResumeVersion`。AI 返回 `ResumePatch`，每个操作包含：

- JSON Pointer 目标路径。
- 修改前值和建议值。
- 修改理由。
- 对应 JD 要求。
- 支持事实 ID。
- 风险标记。

补丁先进入待审状态。用户可以逐项接受、拒绝或编辑；只有确认后的操作才生成新版本。版本支持回退，回退通过切换活动版本实现，不删除历史。

## 5. 用户流程

### 5.1 创建项目

用户在首页创建求职项目，输入项目名称、公司名称、求职类型和 JD。保存后进入工作台。JD 为空时不能开始分析。AI 可以根据 JD 推荐求职类型，但只有用户可以确认或修改该类型。

### 5.2 建立个人事实库

用户可以上传一份简历，或选择“从经历开始”。

上传后，系统展示解析进度、解析质量和结构化内容。低置信度字段必须醒目标记，等待用户确认。若文件无法读取，保留原文件，并引导用户粘贴文本或手动录入。

无简历时，系统先收集最小信息集：目标职位、教育、最近经历、代表项目、技能。AI 根据缺口一次提出一个短问题，用户可以跳过。

### 5.3 JD 分析

系统输出以下结构化结果：

- 岗位名称和职级推断。
- 核心职责。
- 必备技能和加分技能。
- 行业与业务关键词。
- 对成果证明的期待。
- 可能的面试和笔试主题。

推断内容必须标记为推断，并显示其 JD 依据。

### 5.4 匹配与补充

系统把 JD 要求与事实库逐项匹配，分为“已有证据”“证据较弱”“没有证据”。匹配度是可解释的覆盖比例，而不是宣称通过 ATS 的绝对分数。

系统优先询问能显著增强简历且可能真实存在的信息，例如项目规模、职责边界、使用工具和可量化结果。用户回答后生成新事实，用户可以修改或确认。

### 5.5 生成与优化

系统按以下顺序生成建议：

1. 调整目标职位和个人简介。
2. 重排与 JD 最相关的经历和项目。
3. 改写经历要点，突出动作、对象、方法和结果。
4. 调整技能分类和关键词。
5. 压缩重复、空泛或与岗位无关的内容。

所有修改以补丁形式展示，不自动覆盖当前简历。

校招和实习项目额外生成“一页优化建议”：优先删除低相关重复表达、合并技能分组、缩短项目要点并采用更紧凑的间距。系统不得为满足一页而截断文字、隐藏经历或删除事实库内容。

### 5.6 模板选择

- 上传 DOCX：创建导入样式描述，尽量沿用字体、颜色、间距、标题样式和分栏。
- 上传 PDF：根据页面尺寸、文本块、字体层级和颜色生成近似样式描述。
- 上传 TXT 或未上传简历：AI 根据岗位类型、内容长度和经历年限从四套预置模板中选择。
- 用户可以随时切换模板，切换不改变结构化内容。
- 校招和实习项目使用各模板的紧凑排版令牌；社招项目使用自然分页令牌。

四套预置模板为：

- `清晰单栏`：通用、ATS 优先。
- `专业双栏`：技能和证书较多的技术或专业岗位。
- `项目聚焦`：项目经验占比高的岗位。
- `经历纵深`：工作年限较长、经历叙事更重要的岗位。

### 5.7 导出

- PDF：前端调用浏览器打印，使用与预览一致的 A4 打印样式，并提示用户关闭浏览器页眉页脚后保存为 PDF。
- DOCX：按当前结构和模板令牌生成可继续编辑的文档；校招和实习使用紧凑字号、间距和页边距，并在导出前执行容量估算；不承诺与网页逐像素一致。
- JSON：导出完整结构化简历和模板标识，不包含 API Key。

校招和实习预览实时比较内容高度与一页 A4 可用高度。发生溢出时，界面标出贡献最大的章节、提供一页优化建议，并阻止 PDF/DOCX 导出；社招预览允许自然分页。

### 5.8 求职训练

模拟面试包含岗位动机、经历深挖、行为题、专业题和反问建议。每轮显示一题；用户回答后，AI 可以追问，并按“相关性、具体性、证据、结构、表达”给出说明性反馈，不使用伪精确的百分制评分。

笔试练习基于 JD 生成选择、简答、案例或岗位专业题。用户可以请求提示、提交答案并查看解析。产品明确定位为练习工具，不为正在进行的受限考试提供隐蔽代答。

## 6. 界面设计

### 6.1 首页

- 创建项目入口。
- 项目卡片：公司、职位、更新时间和当前阶段。
- API 与 Codex 连接状态。
- 最近导出和训练入口。

### 6.2 工作台

桌面端采用三栏布局：

- 左栏：阶段导航、完成状态、版本历史。
- 中栏：当前表单、问答、分析或差异审阅。
- 右栏：实时 A4 预览、模板选择和页面状态。

窄屏下改为阶段页签，预览可全屏打开。任何 AI 运行状态都显示当前任务、停止入口和已完成结果，避免使用无信息的加载动画。

### 6.3 训练区

- 左侧显示训练类型和题目进度。
- 中间显示对话、作答和反馈。
- 右侧显示本题所依据的 JD 要求和简历事实。
- 训练结束后生成可保存的薄弱项和复习建议。

## 7. 模型接入

### 7.1 OpenAI-compatible API

设置项包括 Base URL、API Key、模型名称、超时和温度。API Key 默认只存在服务进程内存中，也可通过环境变量提供。MVP 调用 OpenAI-compatible 的 `/v1/chat/completions` 协议；业务层不依赖供应商特有返回字段。

模型输出必须经过 Pydantic 校验。格式无效时，系统使用同一模型执行一次只针对格式的修复；仍无效则保留原始响应并返回明确错误。

### 7.2 Codex CLI

Codex 适配器通过后端子进程调用本机 `codex exec`。每次调用创建只包含经过最小化处理的项目上下文的临时目录，并使用只读沙箱和禁止交互审批的设置。调用结束后删除临时上下文；原始上传文件不直接提供给 Codex。

用户首次在项目中使用 Codex 时，界面明确说明简历和 JD 的相关内容会发送给 Codex。未确认时不启动调用。

### 7.3 Codex 聊天续聊

系统生成 Markdown 上下文包，包含目标、JD 摘要、已确认事实、当前简历、待解决问题和输出要求。用户可以复制内容或下载文件，然后在 Codex 聊天页面继续。MVP 不依赖未公开的聊天页面嵌入 API。

### 7.4 未来本地模型

`LocalModelProvider` 与其他适配器实现相同协议。未来接入 Qwen3.8 27B 时，只需要增加运行时配置和连接测试，不改变分析、补丁和训练业务逻辑。

## 8. API 边界

主要本地 HTTP 接口：

- `GET /api/health`
- `GET/POST /api/projects`
- `GET/PATCH /api/projects/{id}`
- `POST /api/projects/{id}/resume/import`
- `PUT /api/projects/{id}/resume`
- `GET /api/projects/{id}/versions`
- `POST /api/projects/{id}/analyze-jd`
- `POST /api/projects/{id}/questions`
- `POST /api/projects/{id}/facts`
- `POST /api/projects/{id}/resume/suggest`
- `POST /api/projects/{id}/resume/apply-patch`
- `POST /api/projects/{id}/export/docx`
- `GET /api/projects/{id}/export/json`
- `POST /api/projects/{id}/practice/sessions`
- `POST /api/practice/sessions/{id}/answer`
- `GET/PATCH /api/settings/providers`
- `POST /api/settings/providers/test`
- `POST /api/projects/{id}/codex-handoff`

长时间 AI 调用使用可取消的请求和明确的阶段状态。MVP 不引入分布式任务队列。

## 9. 错误与隐私处理

- 上传扩展名、MIME 类型和文件大小必须同时校验。
- 解析失败不会创建空白正式版本。
- 解析结果低于质量阈值时必须要求用户确认。
- 网络或模型失败不会丢失编辑器中的本地草稿。
- AI 超时、未授权、额度不足和格式错误使用不同错误提示。
- 导出文件生成完成并通过最小完整性检查后才提供下载。
- 校招和实习 DOCX 的容量估算超出一页时返回 `RESUME_OVERFLOW`，不生成被截断的文件。
- 所有模型调用记录供应商、模型、时间和任务类型，但不在普通日志中记录完整简历、JD 或 API Key。
- 删除项目时同时删除数据库记录和本地上传、导出文件；删除前要求用户确认。

## 10. 测试策略

开发采用测试驱动流程：先编写能够因缺少行为而失败的测试，再实现最小代码。

### 10.1 单元测试

- 简历 Schema 和事实来源约束。
- ResumePatch 路径、冲突、接受、拒绝和版本回退。
- JD 匹配和解释性覆盖计算。
- 模板选择规则和内容不随模板切换而改变。
- 校招/实习一页策略、紧凑令牌、溢出估算和社招自然分页。
- API/Codex 输出校验和单次格式修复。
- 隐私日志过滤。

### 10.2 集成测试

- 使用固定 fixture 解析 DOCX、文本 PDF 和 TXT。
- 使用本地假模型服务器验证 OpenAI-compatible 适配器。
- 使用可替换的进程运行器验证 Codex 参数、上下文最小化和错误映射。
- 生成并重新读取 DOCX、JSON；通过浏览器端到端测试验证打印样式包含 A4 页面规则和非空简历内容。
- SQLite 项目、版本和训练会话生命周期。

### 10.3 端到端测试

使用不含真实个人信息的中文样例完成：

1. 创建项目并输入 JD。
2. 上传简历并确认解析结果。
3. 分析 JD 并回答补充问题。
4. 生成建议并接受部分补丁。
5. 切换模板，确认内容不变。
6. 校招项目内容超出一页时看到溢出提示，优化后恢复导出；社招项目可以保留多页内容。
7. 导出 PDF、DOCX、JSON。
8. 完成一轮模拟面试和一道笔试练习。

## 11. MVP 验收标准

- 一条命令启动前后端，浏览器可以完成所有核心流程。
- 中文 DOCX、文本 PDF、TXT fixture 均能生成可编辑简历数据，并显示解析质量。
- 没有上传简历时，可以通过表单和问答生成完整的中文简历草稿。
- JD 分析的每个结论均能定位到输入 JD；简历改写的事实均能定位到用户来源。
- AI 建议不会自动覆盖当前版本；用户可以部分接受并回退版本。
- 四套预置模板可切换，且不会改变简历内容。
- 校招和实习预览只允许一页且不截断内容；溢出时阻止导出并给出压缩建议。社招允许自然分页。
- 浏览器 PDF 打印预览包含当前活动版本；DOCX、JSON 导出文件均能重新打开并包含当前活动版本。
- OpenAI-compatible 假服务和 Codex 进程适配器测试通过。
- 模拟面试和笔试练习能基于当前 JD 与简历运行并保存记录。
- 核心单元、集成和端到端测试通过，生产构建通过。

## 12. 实施原则

- 先完成事实库、版本和补丁机制，再接入 AI，避免让生成文本成为系统唯一数据源。
- 先支持可靠的结构化内容和预置模板，再逐步提高上传模板还原度。
- 所有模型能力都通过可替换适配器实现，业务代码不感知供应商。
- 不为了 MVP 引入账号、云服务、队列或桌面打包。
- UI 必须支持键盘操作、清晰焦点、减少动态效果选项和窄屏浏览。
