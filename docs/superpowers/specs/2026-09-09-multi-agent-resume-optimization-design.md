# 多 Agent 简历优化与 Loop Engineering 设计

日期：2026-09-09  
状态：已完成讨论，等待最终审阅

## 1. 背景

当前中文 AI 简历工作台已经具备简历录入、JD 分析、修改建议、模板预览、版本管理和面试训练能力。现有 AI 流程以单次调用为主，容易出现三个问题：一次输出同时承担分析、写作和审查，缺少职责隔离；模型只能根据文本长度猜测版面，无法稳定处理短尾行和分页；遇到限流或局部失败时，往往需要重新执行整段流程。

本设计引入多 Agent 协作和有边界的 Loop Engineering。系统将一次深度优化拆成结构化步骤，使用独立审查、真实模板渲染和确定性规则形成反馈闭环，并通过停止条件、检查点和人工确认控制成本与风险。

## 2. 目标与非目标

### 2.1 目标

- 同时提升事实可信度、JD 匹配度、中文表达质量和实际模板排版质量。
- 所有 AI 修改都可以追溯到用户事实、JD 要求或明确的排版问题。
- 校招和实习简历以一页为硬约束；社招允许多页，但避免不自然分页。
- 支持快速优化和深度优化两种模式。
- 深度优化最多返工两轮，并具备明确的完成、等待用户和失败状态。
- 遇到 429、502、超时或结构化输出错误时，只恢复失败步骤。
- 保持现有“逐条查看并接受修改”的产品原则。

### 2.2 非目标

- 不让多个 Agent 进行无边界的自由讨论。
- 不允许 AI 补写用户没有提供的成绩、数据、职责或技术经历。
- 不将内部评分包装成录取概率或招聘成功率。
- 本阶段不增加账号、云同步、本地 Qwen 模型或多模型路由。
- 本阶段不要求每个 Agent 配置不同模型；全部使用用户当前选择的模型服务。

## 3. 用户模式

### 3.1 快速优化

快速优化用于日常小改，执行一次 JD 分析、一次简历优化和一次确定性排版检查。它不启动独立审查返工循环，延迟和 API 消耗最低，是默认模式。

### 3.2 深度优化

深度优化由用户主动选择，依次执行事实与 JD 分析、内容与排版联合优化、真实模板渲染、独立质量审查，必要时最多返工两轮。页面展示当前阶段、已完成阶段、失败原因和可恢复操作，但不展示模型内部思维过程。

## 4. 系统架构

系统采用状态机编排，而不是 Agent 间自由聊天。

### 4.1 编排器

`OptimizationOrchestrator` 负责：

- 创建和恢复优化任务；
- 按顺序调用 Agent、渲染器和确定性校验器；
- 保存每个步骤的输入摘要、结构化输出、耗时、模型用量和状态；
- 根据质量门槛决定通过、返工、等待用户或失败；
- 执行最多两轮的预算和停止规则；
- 保证重试仅作用于当前失败步骤。

编排器不负责写作或语义评分，避免业务规则和模型行为混在一起。

### 4.2 事实与 JD 分析 Agent

该 Agent 接收去除联系方式后的简历事实、公司名称和 JD，输出：

- 岗位职责、硬性条件、加分项和关键词；
- 每项 JD 要求的权重与证据匹配情况；
- 可用于简历的用户事实清单；
- 缺失事实和面向用户的追问；
- 禁止使用的无依据推断。

如果关键事实不足，任务进入 `waiting_for_user`，不会继续生成看似完整但缺少依据的简历内容。

### 4.3 内容与排版联合优化 Agent

该 Agent 接收现有简历、事实证据表、JD 分析、所选模板的排版约束，以及上一轮的渲染和审查反馈。它只输出局部修改操作，不直接覆盖整份简历。

每个修改操作必须包含：

- 修改目标和原文；
- 建议文本；
- 使用的事实 ID；
- 对应的 JD 要求 ID；
- 修改理由；
- 如果由版面触发，包含排版问题 ID 和预期收益。

优化时必须保留相关数字、成果、技术栈和关键 JD 词。允许删除低信息密度的连接词、合并重复职责或重组句式，但不允许为了填充版面而无意义扩写。

### 4.4 排版检测器

排版检测由程序完成，模型不凭字数猜测。每次候选修改都必须套用用户当前选择的真实模板重新渲染，然后生成 `LayoutReport`。

检测项目包括：

- 页数及每页内容占用；
- 正文要点的行数和每行实际宽度；
- 最后一行宽度不足正文可用宽度 25% 的短尾行；
- 标题单独悬在页尾；
- 项目或经历跨页位置不自然；
- 新页只有少量条目；
- 局部过空、过密或明显不均衡。

联系方式、日期列、公司名称、学校名称、章节标题等特殊区域不适用普通正文的短尾行规则。检测器输出元素定位、问题等级和可操作说明，不直接改写文本。

校招和实习超过一页属于硬失败。社招简历不限制页数，但只有少量内容落到新页或存在孤立标题时属于需要优化的问题。

### 4.5 独立审查 Agent

审查 Agent 接收候选修改、事实证据、JD 分析和排版报告，输出结构化评分、驳回项及明确的返工要求。它不能直接生成替换文本，以保持生成与验收职责分离。

审查维度包括：

- 是否存在编造、夸大或无法追溯的表述；
- 是否遗漏重要经历或高权重 JD 要求；
- ATS 关键词是否自然出现；
- 中文表达是否简洁、具体且无重复；
- 是否满足当前求职类型的页数策略；
- 是否仍有严重排版问题。

## 5. 数据流与状态

深度优化任务按以下顺序执行：

1. 固化本次任务使用的简历版本、JD、模板和模型配置摘要。
2. 运行事实与 JD 分析，生成事实证据表和岗位要求表。
3. 如果存在阻塞性事实缺口，保存追问并等待用户。
4. 运行内容与排版联合优化 Agent，生成局部修改草案。
5. 将草案应用到内存中的候选简历，不改变当前正式版本。
6. 使用真实模板渲染候选简历并生成排版报告。
7. 运行确定性校验和独立审查 Agent。
8. 达到门槛则生成最终修改建议；未达到门槛则携带明确反馈进入下一轮。
9. 两轮后仍未达到门槛，停止自动返工并交由用户决定。
10. 用户逐条接受修改后，才创建新的正式简历版本。

任务状态为：

- `queued`
- `analyzing`
- `waiting_for_user`
- `optimizing`
- `rendering`
- `reviewing`
- `retry_wait`
- `ready_for_user`
- `failed`
- `cancelled`

每个阶段产生不可变的结构化产物。恢复任务时，编排器从第一个未成功步骤继续，不重复已经成功且输入摘要未变化的步骤。

## 6. 质量门槛与停止条件

最终候选必须满足：

- 事实可信度：所有新增或增强表述均有事实引用，发现无依据内容即失败；
- 修改可追溯率：100%；
- 高权重 JD 要求覆盖率：不低于 80%；
- 校招/实习页数：不超过一页；
- 严重排版问题：0 个；
- 综合表达评分：不低于 80 分。

JD 覆盖率按要求权重计算，只认可事实能够支持的匹配，不能通过重复关键词提高分数。综合表达评分用于比较同一份简历针对同一 JD 的优化结果，不表示录取概率。

自动循环最多包含初始生成和两次返工。出现以下任一情况立即停止：

- 达到全部硬性门槛；
- 需要用户补充关键事实；
- 达到返工或调用预算；
- 连续两轮评分没有改善；
- 用户取消；
- 出现不可恢复错误。

## 7. 错误恢复与成本控制

- 429 使用带抖动的指数退避，并尊重服务端 `Retry-After`；同一提供商默认低并发执行。
- 502、网络错误和超时只重试当前步骤，并设置有限次数。
- 模型 JSON 不符合合约时允许一次结构化修复；再次失败则保留原始错误摘要并停止该步骤。
- 不自动把失败的深度优化伪装成快速优化；页面可以明确提供“改用快速优化”按钮。
- 以简历版本、JD、模板、模型和提示版本的摘要作为缓存键，复用仍有效的分析产物。
- 每个任务记录调用次数、Token 用量和耗时；超过预算后停止并说明原因。
- 默认将各 Agent 调用串行化，只有互不依赖且不会触发提供商限流的只读检查才允许小规模并发。

## 8. 隐私与日志

- 电话、邮箱、住址等信息不发送给 JD 分析和独立审查 Agent。
- 每个 Agent 只接收完成其职责所需的最小上下文。
- 日志记录任务 ID、步骤、模型、耗时、用量、状态和错误码，不记录 API Key 与完整简历正文。
- 外部模型调用继续遵循现有的数据流向说明，用户能够看到当前使用的服务商。
- 中间候选不会自动覆盖正式简历，只有用户确认后才生成新版本。

## 9. 页面交互

工作台提供“快速优化”和“深度优化”入口，默认突出快速优化。深度优化区域显示：

- 当前阶段与整体进度；
- 已完成的结构化摘要；
- 当前轮次和预算使用情况；
- 等待用户回答、限流等待、失败或取消状态；
- 可恢复、取消和改用快速优化的操作。

最终修改列表沿用现有逐条确认交互，并新增：

- 排版触发原因，例如“消除 3 字尾行”；
- 优化前后页数和版面密度变化；
- 对 JD 关键词的影响；
- 事实和 JD 引用；
- 独立审查结论。

用户看到的是可验证结果与简短理由，而不是模型内部推理过程。

## 10. 持久化建议

在现有数据层增加优化任务和步骤记录，保持与具体数据库实现解耦：

- `optimization_runs`：项目、输入版本、模式、状态、轮次、预算和最终结果；
- `optimization_steps`：步骤类型、输入摘要、输出 JSON、状态、尝试次数、耗时和错误；
- `layout_reports`：模板、页数、密度指标和问题列表。

中间产物使用结构化 JSON 保存。正式简历版本表保持现有职责，不保存尚未确认的候选为正式版本。

## 11. 测试与评测

### 11.1 单元测试

- 状态流转、停止条件、预算计算和缓存键；
- 事实引用完整性、JD 加权覆盖率和评分门槛；
- 429 退避、步骤级重试、取消和恢复；
- 短尾行、孤立标题、分页和求职类型页数规则。

### 11.2 Agent 合约测试

- 每个 Agent 返回符合模式的 JSON；
- 优化操作引用存在的事实、JD 要求和排版问题；
- 审查 Agent 只评分和提出返工要求，不直接生成替换文本；
- 无事实支持的表述被确定性校验拒绝。

### 11.3 集成与端到端测试

- 使用固定测试模型模拟首次审查失败、第二轮通过；
- 模拟 429 后从失败步骤恢复，不重复成功步骤；
- 模拟等待用户补充事实后继续；
- 验证用户未确认前正式简历版本不变化；
- 验证校招、实习一页和社招多页策略。

### 11.4 中文简历评测集

建立脱敏的校招、实习和社招样例，持续记录：

- 事实可信度；
- 加权 JD 覆盖率；
- 严重与一般排版问题数量；
- 人工接受修改的比例；
- 平均调用次数、Token 和完成耗时。

提示词、模型或编排逻辑变更必须在同一评测集上对比，避免用主观印象判断质量是否提升。

## 12. 分阶段交付

第一阶段实现状态机、三个逻辑 Agent、结构化合约、两轮上限和现有排版页数反馈。第二阶段增加基于真实行宽的短尾行与孤立元素检测，并在修改界面展示排版收益。第三阶段补齐评测集、运行统计、缓存和更完整的失败恢复。

三个阶段均保持同一个模型配置入口。后续接入本地模型或多模型路由时，只替换提供商与路由策略，不改变 Agent 合约和编排状态机。
